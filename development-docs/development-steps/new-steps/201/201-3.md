# 201-3 — реестр признаков под памятью

## 1. Что строится
- Конфиг реестра в дереве памяти — **`AGI-CONFIG/`** (имя названо владельцем 2026-09-14, вечное): запись — `key` (вечный) · `title` · `valueType` (text · number · money · date ·
  geo · flag · list · object) · `aggregate` (last · list · sum-able) · `subject` и **глубина** по правилу §3п · `tags` · `triggers` · `answers`
  (слова человека) · `howToFind`. **Без `storedIn`**: таблицу память выводит из ключа по `lib/naming.mjs`.
- Начальные записи: 14 живых родов корневой таблицы (`city_where_he_lives_now` → признак с `aggregate: last`) и 14 признаков `person.*` чата,
  сведённые без дублей; признак расходов (`money`, `list`) — для кейса владельца.
- Сторож `scripts/check-features.mjs` в `build`: закрытые типы, обязательные поля, уникальность ключа, тройка `tags/triggers/answers`.
- Чтение каталогом `GET /v1/features` (и `/v1/features/{key}`) — только смысл; схема `output` в договоре; вкладка API.

## 2. Что считается готовым
У памяти есть свой реестр признаков, читаемый любым потребителем, и каждая запись валидна по сторожу.

## 3. Чем доказывается
- **A:** `GET /v1/features` на сервере отдаёт все записи с ключом, типом и накоплением; сторож зелёный; живые роды сопоставлены признакам
  (счёт: 14 из 14).
- **B (негатив):** запись без `valueType` или с неизвестным типом роняет сторож; `storedIn` в записи роняет сторож; ответ каталога не содержит
  имён таблиц.
